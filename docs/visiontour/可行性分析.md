# 景灵 VisionTour 可行性分析

> 2026-10-15。依据：[需求文档.md](需求文档.md) + 当天实测（脚本 `scripts/probe_vision.py`，可复现）。
> 截止日期 10-25，剩 10 天。

## 结论

**能做，但要改三处，否则核心体验会翻车：**

1. **识别景点不能只靠看图，要先定位。** 只给照片时，qwen3-vl-plus 10 张里只认对 1–2 张，而且会**高置信度认错**（把上海欢乐谷认成杭州乐园、古猗园认成拙政园/豫园，置信度 0.85–0.92）。先用手机定位 + 高德拿到附近景点，再让模型从候选里选，10/10 全对。
2. **“5 秒内出结果”只能靠流式输出和拆分步骤达成。** 一次完整的图片分析就要 4–6 秒；拆成“先认景点（1–2 秒）→ 再出拍照建议”，第一屏能在 2 秒内出来，完整结果约 6–8 秒。
3. **“黄金机位”要收窄为“就在你眼前能做的调整”。** 模型看不到照片以外的地方，它推荐的“去对岸观景平台”“去和平饭店顶层”这类远处机位无法验证，容易编。

另外有两个不改技术就绕不开的问题：**赛道撞车**（#169 已做“拍照识景”）和**技术栈重写不值得**。详见下文。

## 一、实测数据

### 1. 照片识别景点（qwen3-vl-plus，飞猪 10 个上海景点的主图）

| 方式 | 准确 | 单次耗时 | 说明 |
|---|---|---|---|
| 只给照片 | 1–2 / 10 | 2.4–7.3 秒 | 4 张答“未知”（诚实）；3 张**高置信度答错**（0.85–0.92） |
| 照片 + 5 个附近候选 | **10 / 10** | **1.0–3.4 秒** | 输出短，所以更快 |

注意：
- 候选是从全市景点里随机抽的，差异大，比较好选。真实场景下附近景点可能很像（同一园区的几个馆），准确率会低一些，需要用真实定位再测。
- 飞猪主图是营销照片，构图好、地标明显；用户随手拍的照片更难认。
- 答错的都是“长得像的同类景点”（园林认成名气更大的园林、乐园认成别的乐园），说明模型会往知名景点上靠。这正是旅拍场景最怕的：告诉用户“你在拙政园”，用户就不会再信后面的建议。

### 2. 模型可用性

需求文档里的模型都能用：`qwen3-vl-plus`、`qwen3.8-flash` 都在百炼账号的模型列表里（实测 2026-10-15）。

### 3. 飞猪数据

| 需要的数据 | flyai 命令 | 实测 |
|---|---|---|
| 景区门票 | `search-poi` | 有，含票价和跳转链接（现有项目已在用） |
| 附近酒店 | `search-hotel --poi-name` | 有，按距离排序 |
| 旅拍套餐 | `keyword-search --query "上海旅拍"` | **有**，10 条跟拍/约拍商品（外滩、武康路、迪士尼），有标题和跳转链接，**但价格字段为空** |
| 景点附近的拍照点 | — | 没有。只能用 `search-poi` 列出附近景点，或用高德周边搜索 |

另外：flyai 有风控。今天连续约 90 次请求（15 分钟内）后返回 451“Abnormal access behavior detected by risk control”。每次拍照最多调用 1–2 次，并且要缓存。

## 二、逐条评估需求文档

| 需求 | 可行性 | 问题与建议 |
|---|---|---|
| 识别景点/地标 | ⚠️ 要改 | 见结论第 1 条。改为“定位 → 高德周边景点 → VL 从候选中选”；没有定位权限时让用户从列表里点选 |
| 评估光影与构图 | ✅ | 模型擅长，输出也有用（“低角度仰拍，用湖石做前景引导线”） |
| 推荐 2 个最佳机位 | ⚠️ 要收窄 | 能做的是：基于当前画面的调整（往哪站、蹲低、换竖构图、等人走开）+ 姿势建议。远处机位只能来自已知数据（高德/飞猪景点坐标），不能让模型自己说 |
| 输出“构图坐标” | ✅ 可选 | Qwen3-VL 支持输出画面内的框坐标（0–1000 相对坐标），可以在照片上画框标出“人站这里”。这是很好的演示点，但需要调提示词，建议 P1 |
| 意图识别节点（Qwen3.8-Flash） | ✅ 但可以省 | 入口只有“拍照”一个动作时，意图是确定的，不需要意图识别。可以省掉一次调用和约 1 秒 |
| 在百炼控制台编排 Agent | ⚠️ 不建议作为主链路 | 控制台编排不好测试、不好控制耗时和兜底。建议代码里编排（现有项目已经这样做），同时满足大赛“百炼在运行时链路”的要求 |
| 拉取门票、酒店、旅拍套餐 | ✅ | 见上表；旅拍商品没有价格，卡片只显示标题和“去飞猪看看” |
| H5 调起摄像头 | ✅ | `<input type="file" accept="image/*" capture="environment">` 即可；定位需要 HTTPS 部署 |
| 微信小程序 | ❌ 不建议 | 注册、类目资质、审核至少一周，10 天内风险太大 |
| Vue 3 + Koa2 重写 | ❌ 不建议 | 现有 Python FastAPI + 原生 H5 已经接好百炼、flyai、高德、缓存、离线预览，重写没有收益 |
| 全链路 5 秒内 | ⚠️ 要改口径 | 改为“2 秒内出第一屏（认出景点），完整建议流式出来”。纯 5 秒内出全部结果做不到 |
| 评委测试 100% 不报错 | ✅ | 沿用现有做法：录制真实结果做离线预览页 + 线上失败时退回上次结果 |
| 请求报文 | 小错 | OpenAI 兼容接口里 `temperature`、`max_tokens` 放在顶层，不放在 `parameters` 里（那是 DashScope 原生接口的写法） |
| 1 亿 Token 补贴 | ❓ 待核实 | 没查到出处，提交材料里写之前请到百炼控制台确认 |

## 三、赛道风险（比技术风险更大）

- VisionTour 最接近官方命题中的“**AI 私人讲解员**”（拍照听历史）或“**目的地探索**”，都不是我们原来选的“高品质酒店 staycation”。
- 调研报告记录过：**#169 随行讲解员已经实现了“拍照识景 + 分层讲解 + 史实标注”**。评委看到“拍照识别景点”会直接联想到它。
- 差异化必须放在“**拍照**”上，而不是“识景”上：用户关心的是“怎么拍好看”，识别景点只是前置步骤。演示和 Issue 标题要突出“旅拍教练 / 机位”，不要突出“识别景点”。
- 市场前景上，可以讲“拍照建议 → 旅拍跟拍商品”的转化。飞猪确实有这类商品（实测有），这是比讲解员更强的商业故事。

## 四、建议的最小可行链路

```
拍照（H5 摄像头） + 定位（浏览器 geolocation，需 HTTPS）
  └─ 高德周边搜索：附近 1 公里内的景点 → 候选 5–8 个                     不调用 flyai
       └─ qwen3-vl-plus：从候选中认出景点（1–2 秒）→ 第一屏：“你在古猗园”
            └─ qwen3-vl-plus：基于当前画面给 2 条可立即执行的构图/姿势建议（流式）
                 └─ 可选：在照片上画框，标出“人站这里”
            └─ flyai（各 1 次，带缓存）：该景点门票 + 当地旅拍跟拍商品 + 附近酒店
                 └─ 结果页：建议卡片 + 飞猪推荐卡片
没有定位权限 → 让用户从“城市 + 景点名”下拉里选，跳过识别
```

能复用的现有代码：`app/llm.py`（百炼）、`app/flyai.py`（飞猪 + 缓存）、`app/geo.py`（高德）、离线预览生成脚本、FastAPI 骨架。

## 五、10 天排期（单人）

| 天 | 内容 |
|---|---|
| 1 | 高德周边搜索 + 候选识别接口；用真实定位和自己拍的照片测 20 张 |
| 2–3 | 拍照建议提示词：只给画面内可执行的建议；输出 JSON + 流式 |
| 4 | 飞猪推荐：门票、旅拍商品、附近酒店，缓存 + 风控节流 |
| 5–6 | H5 页面：拍照、定位、第一屏、建议卡、推荐卡；HTTPS 部署 |
| 7 | 画框标注机位（时间不够就砍） |
| 8 | 兜底：无定位、识别失败、超时；离线预览页 |
| 9–10 | 实拍素材、录视频、写 SUBMISSION |

## 六、需要你决定的事

1. **是否放弃原来的“住进去”（酒店 staycation）**，整体转到 VisionTour？两者代码可以共用，但演示和提交只能选一个主题。
2. 赛道选“AI 私人讲解员”还是“目的地探索”/自由命题？这决定了如何避开 #169。
3. 能否在 1–2 天内拿到 **20 张自己在景区实拍的照片 + 拍摄位置**？这是验证“附近景点很像时还能不能认对”的唯一办法，也是演示视频的素材。
